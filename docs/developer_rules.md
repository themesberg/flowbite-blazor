## Project Structure Guidelines

### Solution Structure
```

├── build.py                    # Build/run/test automation (use this for everything)
├── docs/                       # Developer rules, memory aid, migration guides
├── scripts/                    # Utility scripts (icon generation)
└── src/
    ├── Flowbite/               # Core component library (net8.0;net9.0)
    │   ├── Base/               # Component base classes
    │   ├── Common/             # Shared types (slots, enums)
    │   ├── Components/         # Components (.razor + .razor.cs)
    │   ├── Icons/              # Built-in icon components
    │   ├── Layout/             # Layouts and hosts (e.g. ToastHost)
    │   ├── Services/           # DI services and AddFlowbite* extensions
    │   ├── Utilities/          # ElementClass, Debouncer, etc.
    │   ├── js-src/             # Rollup source for wwwroot/js/floating-ui.bundle.js
    │   └── wwwroot/            # flowbite.css (Tailwind input), flowbite.min.css, JS modules
    ├── Flowbite.ExtendedIcons/ # Optional icon packs (net8.0)
    ├── DemoApp/                # Blazor WebAssembly documentation site (net9.0)
    │   ├── Layout/             # Site layout and sidebar data
    │   ├── Pages/Docs/         # Component demo pages
    │   └── wwwroot/            # app.css (Tailwind input), app.min.css, llms-docs/
    └── Flowbite.Tests/         # bUnit unit tests + Playwright integration tests (net9.0)
```

## Coding Standards

### C# Conventions
- `src/Flowbite` multi-targets `net8.0;net9.0`; library code must compile for both, so limit language features to C# 12 (collection expressions, primary constructors, etc.)
- Follow Microsoft's C# Coding Conventions
- Prefer Component.razor and Component.razor.cs over Component.razor (all in one file)
- Use `nullable` reference types throughout
- Prefer `async`/`await` for all I/O operations
- Use dependency injection for all services

### Naming Conventions
- **Services**: `I{Name}Service` interface, `{Name}Service` implementation; register via an `AddFlowbite{Name}Service` extension and include it in `AddFlowbite()`
- **Slots**: `{Component}Slots` deriving from `SlotBase` (e.g., `CardSlots`)
- **Enums / options / context**: `{Component}Enums.cs`, `{Component}Options.cs`, `{Component}Context.cs` beside the component
- **Icons**: Suffix with `Icon` (e.g., `ArrowDownIcon`)
- **Demo pages**: Suffix with `Page` (e.g., `AlertPage.razor`)
- **Razor Components**: PascalCase matching filename
- **Methods**: Async methods should end with `Async`


## Documentation Requirements

- Add XML comments to public APIs
- Maintain README.md with setup instructions
- Add a demo page under `src/DemoApp/Pages/Docs/components/` for every new component and a matching section in `src/DemoApp/wwwroot/llms-docs/sections/`
- Update the relevant project `CHANGELOG.md` (`src/Flowbite/`, `src/Flowbite.ExtendedIcons/`, `src/DemoApp/`) before committing a feature

## Testing Guidelines

- Tests live in `src/Flowbite.Tests/`; see [`src/Flowbite.Tests/CLAUDE.md`](../src/Flowbite.Tests/CLAUDE.md) for patterns.
- `python build.py test` — unit tests (bUnit/xUnit); `python build.py test <filter>` for a single class or test.
- `python build.py test-publish` — run after adding or changing DemoApp pages; catches pre-rendering errors.
- `python build.py test-integration` — Playwright smoke tests against DemoApp.
- Before submitting UI changes, also smoke-test DemoApp using `python build.py start` and the Playwright MCP server, in both light and dark themes.

## Git Workflow

- Branch from `develop`: `git checkout develop && git pull origin develop`.
- Naming: `fix/issue-{id}-description`, `feature/issue-{id}-description`, or `enhancement/issue-{id}-description`.
- Commit format: `{type}({scope}): {description}` (types: fix, feat, docs, style, refactor, test, chore). Reference issues with `Fixes #{number}` when applicable.
- Merge feature branches into `develop` with `git merge --no-ff`.
- Ensure `src/Flowbite/wwwroot/flowbite.min.css` and `src/DemoApp/wwwroot/css/app.min.css` are committed if they have changed. They are regenerated by the Tailwind CLI on every `python build.py` build.


## Verification Checklist Discipline

- **NEVER** ask for push/merge approval until ALL verification checklist items are `[x]`
- Before asking "Ready to push?", first re-read the verification checklist
- If any item shows `[ ]`, complete that step first (e.g., runtime testing, UI verification)
- The commit is NOT the completion milestone - the full checklist is
